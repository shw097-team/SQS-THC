> Retrieval eval finding  
> → Slow/Engineering Change

> → last-known-good profile  
> → **下一個適用 Run 才允許 SF-16 啟用**。

這是成熟系統應有的做法。

# 六、所以 Qdrant / pgvector 現在到底應該怎麼裁決？

我重新依**目前真實產品條件**，而不是一般 RAG 專案，給出較明確結論。

目前 SQS 的部署基線是：

> Windows local-first、single-user、single-repo、few-process。

而現行 stack 並沒有把 PostgreSQL 定為基礎 runtime substrate；反而 SQLite 已經被 ADOPT。

在這個條件下，我會把未來 semantic retrieval 第一候選改成：

## **Qdrant = PREQUALIFIED DEFAULT CANDIDATE，DEFAULT OFF**

而不是 Qdrant / pgvector 永遠五五開。

原因有三個。

### Qdrant 對本專案部署形態更吻合

截至 **2026-08-11** 查核，Qdrant 最新正式版是 **v1.19.0，2026-08-05**；這一版仍在大幅增加 storage/memory control、sparse-search IDF、prefix filtering、quota、deterministic routing 等功能，且修補 snapshot path-traversal security issue，顯示目前仍屬非常活躍的專案。([GitHub](https://github.com/qdrant/qdrant/releases))

Qdrant 本身已支援 dense/sparse hybrid、多階段 query、filtering，而且官方提供 snapshot 與 migration tooling。([Qdrant](https://qdrant.tech/documentation/search/hybrid-queries/?utm_source=chatgpt.com)) ([Qdrant](https://qdrant.tech/documentation/search/text-search/hybrid-search/?utm_source=chatgpt.com)) ([Qdrant](https://qdrant.tech/documentation/migration-recovery-options/?utm_source=chatgpt.com))

這很適合：

> SQS Knowledge metadata + owner/source filters + semantic retrieval

的用途。

### pgvector 很成熟，但目前會多帶入一個 PostgreSQL operational substrate

pgvector 本身沒有問題。它支援 HNSW、IVFFlat、exact vector search、iterative scans、partitioning 與 Postgres 原生 filtering；目前 changelog 最新正式版是 0.8.2，2026-02-25，且特別改善 Windows install target。([GitHub](https://github.com/pgvector/pgvector/blob/master/README.md?plain=1&utm_source=chatgpt.com)) ([GitHub](https://github.com/pgvector/pgvector/blob/master/CHANGELOG.md?utm_source=chatgpt.com))

但如果這個產品**本來沒有 PostgreSQL**，只為 semantic retrieval 新增：

> PostgreSQL server + pgvector

其實不一定比一個專用 Qdrant provider 更簡單。

而且 pgvector 官方文件本身說明，ANN + metadata filter 時是先掃 ANN index 再 filter，需要 iterative scan、partial indexes 或 partitioning 等設計；2026 的相關 issue 仍在討論 filter-aware HNSW 的限制。([GitHub](https://github.com/pgvector/pgvector/blob/master/README.md?utm_source=chatgpt.com)) ([GitHub](https://github.com/pgvector/pgvector/issues/980?utm_source=chatgpt.com))

因此我的裁決是：

| 情境 | 優先 |
|---|---|
| 目前 SQS Windows local-first，不採 PostgreSQL | **Qdrant** |
| 未來 PostgreSQL 已因其他核心需求正式採用 | **pgvector 可重新競標** |
| 只需要 exact/lexical/current Daily Run | **SQLite FTS5，不啟用任何 Vector DB** |

# 八、Neo4j：我仍然不建議現在「預設啟動」，但應該提高 readiness

這裡我不會因前面的修正就直接主張：

> 「把 Neo4j 也一起裝起來。」

原因是 current Daily RBWI 並沒有證據顯示它需要 graph-specific runtime 才能完成。

更重要的是，2026 年 6 月的研究對 basic RAG、GraphRAG、Modular RAG、Agentic RAG 做比較時，明確觀察到：

> 更大的 retrieval expansion 並不一定等比例改善最終 generation quality。

也就是「GraphRAG 比較複雜」本身不是採用理由；應該用實際 scenario 驗證 multi-hop / relation-heavy query 是否得到實質增益。([arXiv](https://arxiv.org/abs/2606.25656?utm_source=chatgpt.com))

- 有 KG Builder；

- 也能把 **Qdrant 作 external vector retriever**。([GitHub](https://github.com/neo4j/neo4j-graphrag-python?utm_source=chatgpt.com))
- 最新 1.18.0 又在處理 relationship schema consistency。([GitHub](https://github.com/neo4j/neo4j-graphrag-python/releases))

# 十六、我建議採用的最小修改方案

不重新設計 PKG-DOC-14，也不增加新的 Knowledge 平面，只修改 Tool/Install/WP 控制工件：

1. **SQLite + FTS5 保持 baseline required/default**：在 clean-machine construction wave 就安裝、bind、smoke、negative、grounding、NRTV、backup/restore；SF-16 每日只驗健康與 pin。
2. **Qdrant 提升為 P1 semantic provider candidate**：現在就完成 pin、Install Profile、`RetrievalPort`、benchmark corpus、security/parity/uninstall；runtime 保持 `DEFAULT_OFF`，只有 FTS5 未達預註冊 retrieval threshold 才 enable。
3. **pgvector 保留 P2 conditional candidate**：只有未來 PostgreSQL 本身被正式採用時再競標，避免只為 vectors 新增 PostgreSQL operational stack。
4. **Neo4j GraphRAG 提升為 P1 graph provider candidate，但不 baseline install**：先完成 `GraphRetrievalPort`、edge projection、multi-hop benchmark 與 rollback recipe；只有 relation-heavy use case 通過效果門檻才 install/admit。
5. **在 IP/WP 中新增 `CAPABILITY_READINESS_MATRIX`**：把 `provider selected / install profile ready / sandbox qualified / installed-disabled / admitted-disabled / active` 分開，避免 `DEFERRED` 一個字涵蓋太多狀態。
6. **Fast Loop 不准 install**：所有 install/upgrade/rebind 一律走 Slow/Engineering Change；SF-16 只做 current profile admission/health verification。

這樣既符合你說的：

> 「工作流會需要的能力，不能等使用當下才施工」

也不會變成：

> 「因為未來可能用，就先開 SQLite、Postgres、Qdrant、Neo4j 四套服務。」

# 最後裁決

### 對問題 1

**你的批評有一半是正確而且重要的。**

我先前如果把 `DEFER` 理解為「到時再找人處理」，確實會造成實際使用缺口。

但現行設計本身並沒有完全犯這個錯：它已經定義 SF-16、Tool Owner、Installer、Checker、Platform Operator、Install Profile、Tool Admission Ledger 和完整資格流程。真正尚需補強的是：

> **Qdrant / Neo4j 等 deferred provider 必須在 production go-live 前做到 `READY-TO-ACTIVATE`，不能只有抽象的 future candidate。**

對目前 Daily Run，**SQLite FTS5 是應先實裝與 admission 的 baseline**；Qdrant 建議現在就 prequalify，但 default off；Neo4j 建議建立 provider-ready profile，但不用 baseline 常駐。

### 對問題 2

**不是上游設計缺口，是我前一答遺漏了重要上游內容。**

上游已經明確定義：

> `knowledge_fts.sqlite` + Knowledge Owner + SourceCapsule rebuild policy

更上層 HG-KSEOS 又明確定義：

> `Git Markdown + Source Ledger` 為 canonical knowledge，KG/index 是 derived projection。 

目前真正尚未綁的是**目標 Windows/repository 的實際 path 與 runtime admission evidence**，不是 Knowledge physical ownership 本身。

這個修正後的方案，會比「一律延後」更可施工，也比「所有 DB 先裝滿」更符合目前 SQS/TW-ICT 的工程原意。
